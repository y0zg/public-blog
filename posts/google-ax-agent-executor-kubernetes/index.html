AX: Google's orchestrator for AI agents on Kubernetes

October 9, 2026 · 6 min · Oleksandr Kulbida

In 2014 Google released Kubernetes to manage lots of containers across lots of hosts. Today it’s the de facto standard for running workloads.

In 2026 Google released AX (Agent Executor) to manage lots of autonomous agents inside a Kubernetes cluster. Whether it becomes a standard too, only time will tell.

AX is infrastructure for running AI workloads. It runs on top of Kubernetes and Agent Substrate, which provides the sandboxed execution. The project calls itself “a high-throughput, declarative orchestrator to run billions of autonomous agent workloads in a cluster”. The README also says it will feel familiar if you’ve used Kubernetes, and it does.

AX is in heavy development. The authors say there will likely be major breaking changes before a stable release, so don’t build production on it yet.

Why a separate orchestrator#

Once you have more than a handful of agents, sending requests to an LLM is the easy part. You also need to prepare environments in a reproducible way, limit resources, isolate execution, and figure out why a particular task got stuck.

Agents don’t fit the usual workload types well. They aren’t stateless microservices and they aren’t run-to-completion batch jobs. They build up state, need strict isolation, talk to model APIs and tool servers, and can burn money in a loop if nobody is watching. AX tries to move all of that infrastructure work into its own layer.

The three primitives#

Everything is declared as ax.io/v1alpha1 YAML. There are three kinds:

  1. Task is a job in an isolated sandbox. You set the container image, command, environment variables, and CPU/memory requests and limits.
  2. Workspace is the working environment: Git repositories, MCP servers and skill packages. You can also give it a goal in plain language, like “set up a Go toolchain”, and an agent will prepare the environment before the main command runs.
  3. Model holds the provider and model configuration, generation parameters, and references to the Kubernetes Secrets with credentials.

Every resource lives in an atespace, which plays the role of a namespace. The default one is default.

apiVersion: ax.io/v1alpha1
kind: Task
metadata:
  name: simple-task
  atespace: default
spec:
  image: "gcr.io/ax-substrate/ate-images/ax-task-runner@sha256:3a0dea6ad8b55278685db58aca6e37dc4ba04056831d45bef3aaeafdca43cac6"
  env:
    - name: ENVIRONMENT
      value: "test"
  debug: true # serve guest services so `ax ssh` works; off by default

It runs the default task-runner image with an empty /workspace directory. debug: true is what lets you shell into the sandbox later.

apiVersion: ax.io/v1alpha1

  name: task123

  env:
    - name: ENVIRONMENT
      value: "test"
  image: "gcr.io/ax-substrate/ate-images/ax-task-runner@sha256:3a0dea6ad8b55278685db58aca6e37dc4ba04056831d45bef3aaeafdca43cac6"
  resources:
    requests:
      cpu: "500m"
      memory: "1Gi"
    limits:
      cpu: "2"
      memory: "4Gi"
  workspaces:
    - name: default-workspace
      path: "/workspace"
  debug: true
---
apiVersion: ax.io/v1alpha1
kind: Workspace
metadata:
  name: default-workspace
  atespace: default
spec:
  git:
    - name: origin
      repo: "https://github.com/chalk/chalk.git"
      branch: "main"
  mcp:
    registries:
      - provider: google
        query: "mcp.tags:build"
    servers:
      - name: git-tools
        endpoint: "http://git-mcp.default.svc.cluster.local:8080"
  skills:
    registries:
      - provider: google
        query: "skills.tags:nodejs"
    path: "/.agents/skills"
---
apiVersion: ax.io/v1alpha1
kind: Model
metadata:
  name: default-model
  atespace: default
spec:
  provider: google
  model: gemini-3.8-flash
  secretKey:
    name: gemini-api-secret
    key: GEMINI_API_KEY

A few things to note:

  • resources works the same way as in a Pod spec.
  • The Workspace is declared once and can be bound to as many tasks as you want. Before the command starts, the runner clones the repo, wires up the MCP servers (a fixed endpoint plus whatever the registry query returns) and puts skills under /.agents/skills.
  • The Model is a cluster resource, so rotating a key or switching to a new model version means one ax apply. You don’t have to go through every agent’s env vars. AX’s own components read Models too, for example when they plan a workspace from a goal.

apiVersion: ax.io/v1alpha1
kind: Workspace
metadata:
  name: golang
spec:
  git:
    - repo: https://github.com/golang/go.git
      branch: "my-fix"
---
apiVersion: ax.io/v1alpha1
kind: Task
metadata:
  name: test
spec:
  workspaces:
    - name: golang
      goal: "Ensure that Go tool chain is available and is built from source"
  debug: true

On first boot the runner gives the goal to an agent, and that agent finishes the setup. Your task’s own command then starts in an environment that’s already prepared. Whether that’s reproducible enough for you depends on how much you trust an LLM to install toolchains the same way every time, but it’s a nice option for prototyping.

Working with tasks#

The ax CLI is deliberately shaped like kubectl:

ax apply -f examples/task.yaml
ax get tasks
# NAME      ATESPACE   PHASE     ACTOR     WORKER-IP    AGE
# task123   default    Running   task123   10.20.3.67   1m

ax watch task task123                # stream phase and condition changes
ax ssh task123 -- ls -la /workspace  # look inside the sandbox
ax suspend task task123              # checkpoint and pause
ax resume task task123               # continue where it left off
ax delete task task123

ax watch and ax ssh cover the “why is this task stuck” question. A task has a status.phase (Running, Suspended, Failed, Terminating…) and two conditions: WorkspaceReady and Ready. If a task is hanging before WorkspaceReady, you know the problem is in the environment setup and not in the agent itself.

suspend and resume come from Agent Substrate. Each task is a lightweight actor, and an idle one can be checkpointed and brought back in under a second. That’s how AX packs many tasks onto the same workers instead of keeping a full pod alive for every idle agent.

ax also follows your current kube context, so kubectx works as you’d expect.

Installing it#

You need Agent Substrate in the cluster first. It installs into the ate-system namespace, and AX expects its API at api.ate-system.svc.cluster.local:443:

1

kubectl get svc api -n ate-system

Then the CLI and the control plane:

1
2

go install github.com/google/ax/cmd/ax@latest
make deploy AX_IMAGE_REPO=<your-registry>

make deploy builds the images with ko, deploys Redis and the control plane into ax-system. There’s no Helm chart or prebuilt release yet, which makes sense given how early the project is.

Summary#

AX doesn’t build agents for you. It’s the layer under them: sandboxes, resource limits, workspaces that come up the same way every time, models managed as cluster resources, and a CLI you can use to see what a task is doing. If you’ve built your own version of this out of Jobs, init containers and shell scripts, the concepts will look familiar.

It’s alpha and the API will change, but it’s worth trying on a test cluster.
