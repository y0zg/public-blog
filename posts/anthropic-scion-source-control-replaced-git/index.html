Anthropic replaced git with its own source control: Scion

October 19, 2026 · 6 min · Oleksandr Kulbida

Anthropic doesn’t use git for its monorepo anymore. In five months they moved to their own version control system called Scion, and the reason is simple: agents write too much code for git to keep up.

The numbers#

In May 2026 about 2,500 changes a day were merged into Anthropic’s monorepo. By September it was over 30,000. Most of that growth comes from Claude writing code, not from people.

At that scale the repository itself becomes the problem:

  • the history of main is close to 100 GB
  • a compressed working copy is over 25 GB
  • CI alone does around 25 million checkouts a day, not counting developer machines, agent sandboxes and research jobs

Git is decentralized by design. Every clone is a full copy of the repository, which is great for a human working on a laptop on a plane. It’s terrible when you have millions of short-lived jobs that each need a fresh copy. Anthropic estimated that fetching naively would mean over 600 PB of git traffic per day.

In their own words, source control became “our biggest development bottleneck.”

What they tried before giving up on git#

They didn’t jump straight to writing a new VCS. First came everything you’d find in a “git at scale” talk:

  • partial clones: shallow clones, sparse checkout, promisor remotes
  • internal mirrors: several hundred of them at peak
  • snapshots (“seeds”) of the repo in blob storage that jobs start from

If you’ve run a big monorepo you know where this goes. Mirrors are one more fleet to operate, and it got harder with every jump in merge rate. Snapshots fall further behind main between refreshes, so every job still has to catch up. And making diff and blame work correctly on partial clones takes more and more care.

For comparison, here’s roughly what the “fast clone” recipe looks like on plain git today:

1
2
3

git clone --filter=blob:none --sparse --depth=1 git@example.com:org/monorepo.git
cd monorepo
git sparse-checkout set services/api libs/common

It helps a lot. But you still negotiate with the server for the commit you want, you still need a full tree for the paths you check out, and git log or git blame on that clone quietly lazy-fetches objects or shows a truncated history. Multiply that by 25 million and it stops being a workaround.

How Scion works#

The main idea is to flip git’s assumption. Git assumes clients may be offline, so each one carries everything. Scion assumes clients are always online, and most of them are agents and CI jobs in a datacenter, so that’s a fair assumption.

So the server does the heavy work and the client stays thin:

  • The server owns history. Commits, merges, rebases, blame and path history are computed on the server. Commits are cheap and lock-free.
  • The client has a bounded cache. It doesn’t hold the repo, only a local cache of objects it has actually used.
  • Checkouts are sparse or virtual. Files show up only when something reads them.
  • Everything has an API. A lot of jobs don’t need a working copy at all. A CI step can ask for a diff or write a change through the API. Their automated bisect and revert pipelines are built on that.
  • No full copy anywhere. Data is spread across servers, and there are no packfiles to maintain.

Instead of git commits the unit of work is a changeset: a list of files changed relative to the first parent, with content-addressed pointers to compressed blobs. Refs like main are a compare-and-swap on a single Spanner row. Things like blame and commit-graph skip lists are “derived data”, computed from the parent’s values, so they can add new indexes without changing the client.

The fetch path is layered:

1
2
3
4

scn (client)
  -> scion-daemon      one per node
    -> scion-cache     regional
      -> scion-server  authoritative, reads from Spanner / cloud storage

Each tier only talks to the next one, so a broken cache can’t take down the servers behind it. Negotiation only covers the trees and blobs the client actually asks for, starting from the root tree, which makes fetches resumable and easy to cache.

If this sounds familiar, it should. Anthropic names Google’s Piper and Meta’s Sapling (its Mononoke server) as prior art. Big companies keep coming back to centralized source control once the monorepo gets large enough.

What they got#

  • every cache tier hits over 99%
  • infrastructure is 200x smaller in CPU and memory than the old git mirror setup
  • CI and research checkouts take seconds instead of minutes, about two orders of magnitude faster
  • CI alone got back 25% of its CPU capacity

Seven people and a lot of Claude#

The whole thing was built by a team of seven. Along with Scion they built Antique, a code review tool made for agent-scale changes, plus “half a dozen related systems”. Antique can express semantic approval rules, so a change that only touches comments isn’t treated like a change to sensitive logic. It also runs the merge queue.

They used Claude heavily: for writing code, for adversarial review, and as monitoring agents. One nice detail is that an early snapshot of Claude Mythos Preview rewrote the git-to-Scion ingestion pipeline, and the new version used 20x less memory and ran 4x faster.

So the agents created the load that broke git, and agents helped build the thing that replaced it.

You can’t use it#

Scion isn’t open source and there’s no announced plan to release it. Anthropic is direct about it: “Scion is by no means a suitable replacement for git for general use.” It’s built for one company with a huge monorepo, swarms of agents and a big compute budget, and they say it’s hard to package in a form that would help other organizations.

What they do instead is share the design and point it at git. Their suggestions for the git ecosystem:

  • new server architectures for git
  • a full set of server-side RPCs that forges like GitHub and GitLab could standardize
  • a negotiation protocol that doesn’t have to look like today’s
  • sparse and shallow features that actually compose well

My take#

Most teams won’t hit this wall soon. A repo with a few hundred merges a day is fine on git, and partial clones plus a decent cache go a long way.

But the direction is clear. Merge volume used to grow with headcount. Now it grows with the number of agents you run, and that can go up 10x in a few months, which is exactly what happened here. Git, CI, code review and the merge queue were all designed around human speed. Anthropic just happened to hit that limit first.

If you run lots of agents against one repo, the things to watch are the same ones they hit: clone and checkout traffic in CI, mirror and cache operations, and how much of your pipeline actually needs a working copy versus an API call.
