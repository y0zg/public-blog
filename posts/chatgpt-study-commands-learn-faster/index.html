50 ChatGPT "commands" for learning faster from books, articles and lectures

October 3, 2026 · 10 min · Oleksandr Kulbida

Most people use ChatGPT for reading the same way. Paste an article, type “summarize this”, get back a wall of text that’s about 70% as long as the original. Then you don’t read that either.

A while ago I came across a list of short “commands” that change what the answer looks like. Instead of “summarize”, you write /flashcards or /argumentmap or /actionplan, and the output comes back in a format you can actually use. I’ve been using a handful of them for a few weeks on tech books, conference talks and long RFC-style docs, and some of them are genuinely useful.

One thing to be clear about first: these are not real ChatGPT features. There is no /mindmap button hidden somewhere. They work because the model reads the word, understands what you probably want, and acts on it. /explainsimply works for the same reason “explain this simply” works. It’s just shorter, and once you have a list, you stop writing the same prompt from scratch every time.

That also means they work in Claude, Gemini, or a local model. Results vary a bit, but the idea is the same.

How to use them#

  1. Paste the material into the chat: text, a PDF, a transcript of a lecture, a link if your tool can read it.
  2. Add one command on its own line at the end.
  3. If the result is close but not quite right, add a sentence: /flashcards, 15 cards, focus on chapter 3 only.

That last point matters. The command sets the format, and a few plain words of context make it much better.

The full list#

Summaries and explanations without the fluff#

Command What you get
/executivesummary The main idea, the author’s arguments and conclusions
/fullsummary A detailed retelling with sections and subsections
/quicksummary The essence in a few short bullets
/chapterbychapter Each chapter summarized in the author’s order
/coreideas The key ideas the topic falls apart without
/studynotes Ready-made notes: source, thesis, concepts, takeaways
/explainsimply Plain-language explanation, no jargon
/explainwithexamples Every concept tied to a real-life example
/glossary A mini-dictionary of terms with clear definitions
/questionsanswered The main questions about the topic, with answers

Examples#

A list of fifty commands is easy to save and never use, so here’s what a few of them actually produced for me. For all of them I used the same source: The Twelve-Factor App, which I wrote about before. It’s short, well known, and has opinions, so it’s a good test. Outputs are trimmed a little but otherwise as I got them.

- Twelve-Factor is a methodology for building SaaS apps that are easy
  to deploy, scale and keep running.
- Keep one codebase per app, declare dependencies explicitly, and put
  config in environment variables, not in code.

Seven bullets instead of twelve sections. Good enough to decide whether to read the whole thing.

Q: Where should config that varies between deploys live?
A: In environment variables.

Q: What's the difference between a build and a release?
A: Build = code + dependencies compiled. Release = build + config for
   a specific environment.

Q: Can a twelve-factor app rely on sticky sessions?
A: No. Session state goes to a backing service like Redis.

Q: How does a twelve-factor app handle log routing?
A: It doesn't. It writes to stdout, the environment routes it.

Q: What does "disposability" mean here?
A: Processes start fast and shut down gracefully on SIGTERM.

Q: Why are admin tasks run as one-off processes?
A: So they run against the same release and config as the app.

Q: How do you scale a twelve-factor app?
A: Horizontally, by running more processes (the process model).

Q: What's a "backing service"?
A: Anything the app uses over the network: DB, queue, SMTP, cache.

/critique#

This is the one I use most, because summaries only tell you what the author thinks.

Output (shortened):

 1

1. Written in 2011 for Heroku-style PaaS. Some advice is shaped by
   that platform, e.g. "logs to stdout" assumes something else
   collects them.
2. "Config in env vars" doesn't address secrets well. Env vars leak
   into crash dumps, child processes and `ps` output. Most teams now
   use a secrets manager and inject at runtime.
3. Says nothing about observability beyond logs: no metrics, traces
   or health checks.
4. Assumes stateless processes are always possible. Stateful
   workloads (databases, stream processors) are out of scope, but the
   document doesn't say so.
5. No guidance on API versioning, backwards compatibility or
   dependencies between services.

Points 2 and 3 are exactly what people add when they talk about “15-factor” apps, so the model is on solid ground here. It’s not always this good. Sometimes /critique invents problems just to fill the list, so treat it as a starting point for your own thinking, not a verdict.

/feynmanmethod#

This one works differently. It doesn’t explain anything, it asks you to:

1
2
3

Explain in your own words, as if to a junior developer, why config
should be stored in environment variables. I'll point out what's
missing or wrong.

I wrote two sentences, it told me I forgot the “same build goes to every environment” part, which is the actual point. Annoying, and useful.

Notice the context in the prompt. Without “Django monolith on EC2”, you get generic advice like “adopt containerization”. With it, you get something you could put in a sprint.

Combining them#

They chain well. My usual flow for a technical book chapter:

1

/coreideas

then, in the same chat:

1
2

/critique
/flashcards, only for things I'd likely forget in a month

/fullstudy does all of this in one go, but the output is huge and I end up scrolling past half of it. Two or three targeted commands are better.

Making them permanent#

Typing the command still relies on the model guessing what /studynotes means. If you want consistent results, define them once.

ChatGPT: put the definitions in Settings → Personalization → Custom instructions, or make a custom GPT:

When my message ends with a command starting with "/", format the
answer as follows:
/studynotes: source, thesis in one sentence, 5-10 key concepts with
  one-line definitions, 3 takeaways. No intro, no outro.
/flashcards: Q/A pairs, answers under 20 words, Anki-friendly.
/critique: numbered list of weak points, each with a reason. Say
  "nothing significant" if there isn't anything.

What doesn’t work well#

  • The visual ones in plain chat. /infographic, /sketchnote and /comicstrip need an image model. With image generation on you get something, but text in generated images is still often garbled. Ask for Mermaid or a table instead when you want something usable.
  • Long books. Paste a 400-page PDF and /chapterbychapter will be confident about chapters it barely read. Go a chapter or two at a time.
  • Facts. /mythsvsfacts and /evidence sound authoritative. The model can still be wrong. If it matters, check the source.
  • Learning by itself. Reading a summary of a summary feels productive. It isn’t the same as working through the material. The commands I keep coming back to are the ones that make me do something: /flashcards, /activerecall, /feynmanmethod, /critique.

Save the list, pick three or four that fit how you learn, and ignore the rest.
