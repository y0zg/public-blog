k8s-aibom: finding out which AI workloads are actually running in your cluster

October 5, 2026 · 9 min · Oleksandr Kulbida

At some point someone from security or compliance asks the platform team a simple question: “Which models are we running in production, and where?” Usually nobody has a good answer. There’s a spreadsheet that was correct six months ago, a few Helm charts that mention vLLM, and that one team that deployed Ollama in a dev namespace “just to try something” and forgot about it.

k8s-aibom is an open source controller from Google Cloud that tries to answer this question by looking at the cluster itself. It watches your workloads, figures out which ones are AI-related, and writes a CycloneDX 1.6 ML-BOM for each of them. So you get a machine-readable bill of materials for every inference server, agent app, vector database, training job and eval harness it can recognize.

Build-time vs runtime#

Most SBOM and AIBOM tools run in CI. They scan the source, the dependencies or the image and tell you what you meant to deploy. That’s useful, but it misses everything that never went through your pipeline: a manual kubectl apply, a Helm chart from a vendor, a model swapped through an environment variable on a Friday evening.

k8s-aibom works from the other end. It reads the live state of the cluster through the Kubernetes API and records what is actually there. It doesn’t replace your build-time scanning, it fills the gap next to it.

What it can detect#

It looks at Deployments, StatefulSets, DaemonSets, Jobs and CronJobs, plus some AI-specific CRDs: KServe InferenceService, NVIDIA Dynamo DynamoGraphDeployment, NIM Operator NIMService and LeaderWorkerSet. From image names, container args, env vars, annotations and volume mounts it tries to recognize:

  • Inference runtimes: vLLM, TGI, Triton, Ollama, Ray Serve, llm-d, SGLang, LMDeploy, TEI
  • Agent frameworks: LangChain/LangGraph, AutoGen, CrewAI, Langflow, Flowise, Chainlit, plus which external LLM APIs they call (OpenAI, Anthropic, Google, Cohere)
  • Vector DBs: Milvus, Qdrant, Weaviate, Chroma, pgvector
  • Training: PyTorch, JAX, KubeRay, Hugging Face Accelerate, and mounted datasets
  • Evaluation: lm-evaluation-harness, Ragas, TruLens

The architecture is pleasantly boring. It’s one unprivileged Deployment in its own namespace. No DaemonSet, no sidecars, no eBPF, no node access. You don’t touch your app manifests or pipelines either.

The flip side is that it only sees what Kubernetes sees. If your Python app loads a model from a hardcoded path and never mentions it in args, env or annotations, the controller won’t know. It doesn’t look inside the process.

Installing it#

When the project was announced in the summer you had to build the image yourself. That’s no longer the case: releases now come with a signed multi-arch image and a Helm chart in GHCR. You need Kubernetes 1.27 or newer.

1
2
3
4

helm install k8s-aibom oci://ghcr.io/googlecloudplatform/charts/k8s-aibom \
  --version 1.5.1 \
  --namespace k8s-aibom-system \
  --create-namespace

After the install nothing happens yet. The controller only reports on namespaces you opt in:

1

kubectl label namespace ml-serving aibom.k8saibom.dev/enabled=true

I like this default. You can roll it out one team at a time and you won’t wake up to a few thousand new CRs.

deployment-vllm-llama3   Deployment   vllm-llama3   inference   vllm      True    12s

The BOM is stored base64-encoded in status.bomDocument (when it’s under 256 KB, larger ones go to an external sink and the CR keeps a URL). To read it:

1
2

kubectl get aibom deployment-vllm-llama3 -n ml-serving \
  -o jsonpath='{.status.bomDocument.inline.data}' | base64 --decode | jq .

The raw document is long, so here is a jq filter I use to get a short table of components with their confidence and where the controller found each one:

1

kubectl get aibom deployment-vllm-llama3 -n ml-serving \
  -o jsonpath='{.status.bomDocument.inline.data}' | base64 --decode |
jq -r '.components[] |
  [ .type, .name,
    (.properties[] | select(.name=="aibom.confidence") | .value),
    (.properties[] | select(.name=="aibom.evidence.locator") | .value) ] | @tsv'

Notice what’s not in there: the value of HF_TOKEN. Secret values never end up in a BOM. For API keys the controller records only the env var name, and every string goes through a redaction filter before it leaves the cluster.

Confidence levels#

That third column is the most useful part of the whole project, in my opinion. Every attribute carries a confidence flag and a pointer to where it came from:

  • declared: you wrote it yourself in the spec. --model meta-llama/Llama-3.1-8B-Instruct is declared.
  • inferred: the controller guessed from a pattern. “This is vLLM because the image matches ^vllm/.*” is inferred.
  • verified: a declared model identity whose Sigstore/OMS signature the controller checked against trust roots you configured. This was added in v1.5.0.
  • unresolved: it knows something is there but can’t pin it down, for example an image digest for a pod that hasn’t pulled yet.

When an auditor reads “this service runs vLLM and serves Llama 3.1 8B”, they can tell which part your team stated and which part a regex guessed. And the evidence locator tells them exactly where in the spec to look. The project also prefers to say “unresolved” over making something up, which is the right call for a compliance tool.

The kubectl plugin#

Decoding base64 by hand gets old quickly. There’s a kubectl aibom plugin on krew:

kubectl krew install aibom

# table of everything in a namespace: workload, category, runtime, models, confidence
kubectl aibom summary -n ml-serving

# decoded, pretty-printed BOM
kubectl aibom view deployment-vllm-llama3 -n ml-serving

# check the stored document against its published sha256
kubectl aibom verify deployment-vllm-llama3 -n ml-serving

The command I’d actually use during an incident is find. Say a CVE drops for a specific vLLM version or someone asks “are we still serving that model anywhere?":

1
2
3

kubectl aibom find --runtime vllm -A
kubectl aibom find --model meta-llama/Llama-3.1-8B-Instruct -A
kubectl aibom find --image vllm/vllm-openai:v0.6.3 -A

Filters combine with AND. One caveat that the docs point out themselves: 0 matches doesn’t prove the thing isn’t running. Namespaces that aren’t opted in and images the detector doesn’t recognize are simply invisible.

Shipping BOMs out of the cluster#

By default nothing leaves the cluster, the BOMs live only in the CR status. For an audit trail you’ll probably want to archive them. Sinks are configured in an AIBOMControllerConfig named default:

apiVersion: aibom.k8saibom.dev/v1alpha1
kind: AIBOMControllerConfig
metadata:
  name: default
spec:
  sinks:
    - name: audit-archive
      type: GCS
      gcs:
        bucket: my-aibom-archive
        pathTemplate: "aibom/{namespace}/{kind}-{name}/{timestamp}.json"
        workloadIdentity: k8s-aibom-controller@my-project.iam.gserviceaccount.com
    - name: graph-ingest
      type: Webhook
      webhook:
        endpoint: https://guac.internal.example.com/ingest
        auth:
          bearerToken:
            secretRef:
              name: graph-ingest-creds
              key: token

If a sink needs to read a Secret (like the webhook token above), install the chart with --set rbac.sinkSecretAccess=true. It’s off by default, so with no sinks configured the controller has no Secret permissions at all.

The GCS sink is designed around the idea that nobody can rewrite history. The controller’s service account only needs roles/storage.objectCreator, with no read or delete rights:

1
2
3

gcloud storage buckets add-iam-policy-binding gs://my-aibom-archive \
  --member="serviceAccount:k8s-aibom-controller@my-project.iam.gserviceaccount.com" \
  --role="roles/storage.objectCreator"

Every write also uses a DoesNotExist precondition, so if an object already exists at that path, the write fails. Even if one of your AI workloads gets compromised, it can’t quietly replace old BOMs. If you’re not on GCP, the webhook sink works with any HTTPS endpoint. One option is to point it at an OpenSSF GUAC collector to get the BOMs into a supply-chain graph.

A nice detail: if you break the config, the controller keeps running on the last config that was valid and reports the problem through conditions and Events on the CR. A typo in a sink won’t stop BOM generation.

Tracking changes with git#

The BOMs are deterministic. The same input gives byte-identical output, apart from timestamps. That makes them easy to diff. Here’s a quick script I’d run from a CronJob or CI to snapshot the inventory into a git repo:

#!/usr/bin/env bash
set -euo pipefail

out=aibom-snapshots
mkdir -p "$out"

kubectl get aibom -A -o json |
jq -c '.items[] | {ns: .metadata.namespace, name: .metadata.name, data: .status.bomDocument.inline.data}' |
while read -r item; do
  ns=$(jq -r .ns <<<"$item")
  name=$(jq -r .name <<<"$item")
  data=$(jq -r .data <<<"$item")
  [ "$data" = "null" ] && continue   # skip BOMs offloaded to an external sink
  mkdir -p "$out/$ns"
  # drop timestamps so diffs show only real changes
  base64 --decode <<<"$data" |
    jq -S 'del(.metadata.timestamp) | walk(if type=="object" and .name=="aibom.scrape.0.timestamp" then empty else . end)' \
    > "$out/$ns/$name.json"
done

git -C "$out" add -A
git -C "$out" diff --cached --stat

Now “someone bumped vLLM from 0.6.3 to 0.7.0 in prod” or “a new LangChain app started calling the OpenAI API” shows up as a normal git diff that you can review, alert on or attach to a change ticket.

Cost#

You’d expect a cluster-wide watcher to be heavy, but the published numbers are tiny. On GKE with about 1,000 tracked workloads, steady state is around 1–2m CPU and ~65Mi of memory, with less than one API server request per minute once things settle. The chart’s default requests (50m/128Mi) are already far above that.

Compliance, briefly#

The project maps its output to the EU AI Act (Articles 12 and 50), NIST AI RMF and ISO/IEC 42001. To be clear, it doesn’t make you compliant with anything. What it gives you is evidence: a current, timestamped list of AI systems with provenance for each claim. That’s the part every one of these frameworks asks for and the part teams usually build by hand.

Where it runs#

It isn’t GKE-only, even though Google is behind it. It runs on GKE Standard and Autopilot, EKS, AKS, OpenShift, kubeadm clusters and kind/minikube/k3s. The only GCP-specific piece is the optional GCS sink.

Should you try it?#

The project calls itself production-suitable for non-critical observation use, and it’s still not an officially supported Google product. For an inventory tool that only reads the API and runs unprivileged, I think that’s fine. The risk of installing it is low, and the biggest thing you’ll probably learn is how many AI workloads you didn’t know about.

My suggestion: install it, opt in one namespace that you know well, check that the BOMs match what you expect, and then roll it out further. If it misses a runtime you use, detection patterns are the easiest way to contribute. The maintainers say they review pattern PRs within 48 hours.
